# SimEval 项目开发流程

| 项目 | 当前事实 |
|---|---|
| 产品 | 面向具身智能团队的评测数据工作台，以数据质量、模拟评测、版本对比和异常证据支撑人工结论 |
| 开发方式 | 规格驱动、按垂直功能切片交付；每批同时处理界面、服务端、持久化、校验和必要测试 |
| 已交付主线 | 访问控制 → 配置与质量确认 → 模拟评测与任务管理 → 同口径比较 → 异常样本复核 |
| 当前边界 | 主页已实现；阶段 8 评测助手与报告已完成本地实现，真实模型接通，页面验收及生产发布待完成 |

## 1. 开发方法

整个项目按“**确定问题与范围 → 写产品需求 → 定架构与数据／接口 → 做体验原型 → 规格、计划与任务 → 实现一个可用切片 → 技术检查与浏览器验收 → 发布和反馈**”推进。功能规格先描述用户行为及可观察的完成标准，计划再确定文件、数据库和权限边界，任务清单用于实施和核对；生成文档本身不算功能完成。

一个“切片”不是只画一个页面或只加一张表。例如创建评测同时涉及配置表单、目录兼容规则、质量门禁、服务端 API、Prisma 持久化、状态反馈和测试。产品负责人决定范围与体验，开发代理协助实现和验证；产品内的 AI 分析服务是另一项业务能力，不能把开发工具当作已上线的 AI 功能。本项目采用规格驱动开发（SDD），不宣称所有功能都经历了“先写失败测试”的严格 TDD。

## 2. 从产品定义到上线的实际过程

### 阶段 0：产品定义

先界定目标用户、核心问题和“配置 → 质量 → 执行 → 对比 → 证据 → 结论／报告”的黄金路径，再确定 MVP 与不做的事。需求来自岗位和领域分析，**没有真实用户调研数据**。报告是完整产品目标，但在前几轮切片中保留为规划；真实仿真、模型训练、实时数据扫描、独立回补任务和人工分类步骤不纳入当前 MVP。

**交付**：PRD、角色权限、主要业务规则、固定合成演示故事与验收口径。演示故事使用“总体成功率 76%→81%，遮挡碰撞率 8%→13%”，用于说明总体改善可能伴随局部回退，不代表真实业务收益。

### 阶段 1：架构、数据与接口

选择 Next.js、TypeScript、Auth.js、Prisma 的模块化单体：路由组织页面，应用层处理完整用例，领域层判断规则，仓储层访问数据库。评测计算先通过 Provider 接口接入确定性 Mock，避免把模拟结果冒充真实执行。设计项目、模型版本、数据集、Benchmark、评测任务、指标、异常、结论历史和审计的数据关系；HTTP 契约统一会话、角色、参数、成功／错误结构和请求 ID。

**交付**：模块边界、Prisma Schema、OpenAPI、身份和状态规则。关键取舍是保留将来替换 Provider 的接口，但当前不引入微服务、消息队列或 WebSocket。

### 阶段 2：体验设计

在 Figma 中先梳理角色入口、六个工作板块、任务选择和主线流转，再补等待、失败、取消、空数据、无权限、窄屏和键盘路径。设计调整不是只换视觉：原先混在一起的创建和对比入口被拆开；从顶层板块进入先选任务，流程内前进／返回持续携带同一个任务。报告等未开放功能在原型中标明状态。

工程实现后又用实际运行页面回对原型，整理现行画框与历史稿，修正页面尺寸、侧栏展开、英文任务名和角色文案。**Figma 是设计与视觉快照**，不能证明数据库写入或权限已经实现。

### 阶段 3：工程基础与身份入口

搭建 Next.js 应用、数据库结构、迁移和可重复的 Seed 数据；接入真实会话、受保护页面、角色导航及基础总览。最初的本地工程使用 MySQL，后来因线上方案改为 PostgreSQL，旧迁移已归档。双身份及服务端权限逐步替换早期单一演示入口。

**验证**：迁移与重复 Seed、登录／退出／刷新、直接访问保护、角色切换、桌面与约 375px 窄屏；规则和会话用单元测试，真实数据库协作用独立测试库。网页按验收清单人工走查，不能用“页面能打开”代替身份和持久化检查。代表性提交：`6054eb4`、`289c5f2`。

### 阶段 4：数据质量、模拟评测与任务管理

按“自主配置 → 质量确认 → 新建任务 → 查看状态／结果”完成第一个核心业务切片。服务端重新验证模型、数据集和 Benchmark 兼容性；PASSED 可创建，WARNING 须明确接受，FAILED 阻断。基线可不选；成功率目标只判断达标，不改变模拟指标。

确定性 Mock 根据配置快照、Seed 和 Episode 数生成合成结果。GET 只读取；POST 同步操作按服务器时间推进 QUEUED、RUNNING 和终态，不伪造后台执行或百分比。随后补多任务选择、同任务上下文、每位工程师最多 3 个进行中任务、取消、失败后新 ID 重试、终态软删除，以及幂等和审计。

**验证**：三种质量门禁、无基线创建、状态恢复、取消／重试／删除、重复提交、并发容量、角色越权和窄屏。数据库集成测试使用独立测试库，避免污染演示数据。代表性提交：`b2d7eb0`。

### 阶段 5：模型对比与异常复核

先实现相同项目、数据、Benchmark、Episode 和 Seed 的版本比较，再从总体／场景指标进入异常样本证据。差值保留单位、方向与样本数；没有基线或不能比较时不把缺失值当成 0。异常详情提供日志、草稿、最终结论和修改历史：工程师可保存本人任务草稿，评测人员可确认最终结论。

保存时传入当前版本号；并发冲突返回 409，不覆盖别人刚写的内容。当前结论、历史、审计以及旧报告过时标记在事务中保存。补齐双向导航后，用户在结果、对比、异常和报告占位页之间往返，不会丢失任务及筛选条件。

**验证**：同口径／不可比、指标下钻、两身份权限、草稿与确认、双窗口版本冲突、刷新恢复、历史与 375px 页面。报告生成和确认没有在此阶段交付。代表性提交：`32c2f89`。

### 阶段 6：换库与部署

线上选择 Vercel 承载 Next.js、Neon 提供 PostgreSQL。迁移不是“每次启动重建数据库”：先将当前 Schema 转为 PostgreSQL 初始迁移，旧 MySQL SQL 归档；再在新库应用迁移和 Seed，旧库数据不自动搬迁。运行时使用池化连接，迁移和维护使用直连；开发分支、独立集成测试库与生产库分开。

本地 PostgreSQL 适配阶段曾通过 87 项单元、18 项独立 PostgreSQL 集成、lint、类型检查与生产构建，并在隔离预览中走查主线。随后 Neon 生产库完成首次迁移和 Seed，保存十条核心合成任务；访问入口改为共享访问密码、双身份与最长 12 小时的 JWT Cookie 会话，并加入连续输错限制。网站发布到 Vercel，域名由 Cloudflare 管理 DNS／代理；不同网络的可达性仍需分别实测，不能因为某一部设备可打开就声称所有大陆网络稳定。

**部署流程**（代码、数据库、域名是三处独立配置）：

1. **准备代码**：将公开仓库连接到 Vercel；GitHub Actions 在 push／PR 时检查代码，Vercel 根据提交构建网站。代码检查、构建和线上业务验收分别核对。
2. **准备数据库**：在 Neon 建立独立的开发与生产分支。生产运行使用连接池地址，数据库迁移使用同一生产分支的直连地址；本地开发和集成测试不连接生产库。
3. **配置生产环境**：在 Vercel Production 填数据库连接、`AUTH_SECRET` 和 `ACCESS_PASSWORD`。这些值只放环境变量，不写进仓库；运行时的池化地址与迁移使用的直连地址须指向同一分支和数据库。
4. **初始化生产库**：首次上线先应用 Prisma 迁移，再写入固定的合成演示 Seed，然后部署或重新部署应用。后续只有新增迁移时才执行相应迁移；普通代码发布不会自动重置数据。
5. **接入域名与 HTTPS**：在 Vercel 绑定自有域名，按其显示的目标在 Cloudflare 配置 DNS，核对域名状态及 HTTPS。域名注册、DNS 解析和网站托管各司其职；能解析到 IP 不等于网页可用。
6. **检查访问与数据**：从不同设备和网络打开域名，输入访问密码，分别体验两种身份；完成创建评测、查看结果、刷新后再读取、对比和复核。检查错误页及服务端日志，记录尚未验收的网络环境。
7. **维护演示数据**：需要回到初始故事时，先确认目标是开发还是生产，再使用对应的后台恢复脚本；生产恢复会删除新增业务数据和人工修改，普通访问与发布都不会触发恢复。

环境变量、首次迁移与 Seed、恢复命令及详细验收步骤见仓库内的 [PostgreSQL 运行与部署验收](../specs/004-deployment/quickstart.md)。以上是本项目采用的流程；其中线上完整持久化验收仍按下文状态单独记录。

GitHub Actions 已配置 push／PR 时运行 lint、类型、单元、独立 PostgreSQL 集成和构建。**CI 检查、Vercel 构建和线上操作验收分别确认**；任意一步成功都不能代替另一步。恢复脚本在事务内清理业务记录并重建默认 Seed，但不能因脚本存在就视作生产恢复已演练。代表性提交：`50b4acf`、`5f15749`、`4d06e76`。

截至本文整理时，公开的部署任务清单尚未记录完整的线上持久化验收。域名能打开和生产构建成功说明发布可访问，不能替代线上创建、刷新后读取、角色权限与故障恢复的逐项检查。

### 阶段 7：交互主页

先独立验证人物动作，再以 Figma 的双侧对话框布局为参考重做公开主页。左侧呈现需求、架构、原型、规格驱动开发与开发步骤；右侧说明产品和可用流程，统一进入既有访问密码页。文案与外链集中在内容文件，动画引擎与排版分离，后续修改介绍无需修改动作代码。

人物使用四段视频抽取的高清 WebP 序列帧，鼠标控制播放进度；换向沿旧动作回待机，再进入新动作。全量压缩素材加载并解码验证后显示，设置真实进度、失败重试和静态入口；有限缓存与提前解码平衡内存和回程流畅度。手机按钮、键盘和减少动态效果均有对应行为。当前已接入工程，本地检查与正式公网发布分别记录，不能把本机加载时间当作线上速度。

### 阶段 8：评测调查 Agent 与报告

先固定单 Agent、四个只读业务工具、登录后 Q 版入口和会话隔离，再采用 LangChain createAgent 与 assistant-ui LocalRuntime 接入既有 Next.js 单体。工具复用评测／比较／复核服务，模型根据问题选择查询；程序验证证据引用、限制调用次数与预算，数据库保存历史与真实记录。

每次登录新增访问标识，解决同一演示角色多人共用时的聊天串线。Agent 只负责聊天调查，报告页独立维护每个任务的一份系统报告：固定模板整理当前指标与人工结论，来源未变化时复用，变化时更新原 ID 并恢复待确认。确认检查用户所读的来源指纹及最新数据；更新前正文与确认信息写入审计。没有引入文档 RAG、独立 LangGraph 服务或长期记忆。

进一步收拢页面职责：取消独立总览，任务状态、配置、指标和待复核数集中在结果页；旧地址仅做兼容跳转。保留旧报告记录，迁移将每个任务最新的旧模板报告标为当前，其余不展示。报告不依赖聊天会话，也不使用模型额度。本轮已核对开发与生产连接不同，在开发库完成增量迁移，原有任务、样本、复核、聊天与报告记录均保留；本轮 lint、类型检查与构建通过，页面及双访客冲突仍待手工验收。

开发库仅增量迁移，未重置。真实模型检查完成一次工具查询和带引用回答；lint、类型与构建通过。本阶段按约定由负责人手工验收，不增加 Agent 自动化测试，线上配置／迁移／真实调用另行验证。部署时增加模型密钥与累计预算，不能把本机代理地址复制到云端。

### 阶段 9：最终验收

完整主线、故障恢复、真实网络和首访时间仍需验证，再形成最终汇报。“几分钟看懂”是目标，不是实测结论。

## 3. 每一批功能如何落地

| 步骤 | 具体产物 | 完成判断 |
|---|---|---|
| 固定范围 | PRD 和功能规格写用户、对象、权限、异常状态与不做的事。 | 不存在“按钮有了但写入、权限或恢复规则没定”的关键歧义。 |
| 设计实现 | 计划定文件、Schema／迁移、接口与事务边界；任务按依赖排序。 | UI、服务端、持久化和校验属于同一切片，未实现的部分明确标记。 |
| 代码验证 | lint、TypeScript、相关单元测试、独立数据库集成测试、生产构建。 | 测试对应实际变更；历史通过记录不能替新行为签收。 |
| 体验验收 | 在浏览器走主线、权限、刷新、空／错／加载、窄屏和键盘。 | 用户能完成真实操作；发现问题修复后复验受影响路径。 |
| 交付记录 | 更新规格、OpenAPI、README 与验收结果；再提交和发布。 | 文档与代码一致，已完成和计划状态分开；密钥与私人材料不进入公开仓库。 |

## 4. 当前交付与限制

当前公开仓库包含可运行应用、PostgreSQL Schema／迁移、固定 Seed、业务接口、单元和集成测试，以及按功能维护的规格。已实现 23 项业务 HTTP 操作，覆盖原有业务、私人聊天与共享报告；仅指派和重开两项保留计划契约。访问密码是共享演示门禁，不是个人账号体系。

因此当前可以完整展示“质量确认 → 模拟评测 → 对比 → 异常证据 → 人工结论”，新增真实 AI 聊天、证据回答与独立系统报告生成／更新／确认的本地实现；阶段 8 页面验收待完成，仍不运行实时仿真。仓库中的历史 MySQL 文档与早期 Figma 画面应按当时切片理解；当前运行架构以 PostgreSQL 代码为准。线上功能、网络可达性和性能必须分别验证，不能仅凭提交记录、设计稿或一次成功打开页面推断。
