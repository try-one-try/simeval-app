# SimEval 开发流程

SimEval 是具身智能模型评测平台，按“产品定义 → 架构与数据设计 → Figma 原型 → 功能实现 → 部署 → 主页 → 评测调查 Agent 与系统报告”的顺序完成。主要体验流程是配置评测、确认数据质量、执行模拟评测、查看结果与按需对比、复核异常样本、生成并确认报告。

本文说明实现顺序、每轮功能怎样交付，以及如何运行和维护项目。产品行为见 [PRD](PRD.md)，技术边界见 [架构与接口](架构与接口.md)，HTTP 参数与响应以 [OpenAPI](openapi.yaml) 为准。所有评测数据和执行结果均为明确标注的合成／模拟内容；聊天调查调用真实模型，系统报告由程序模板生成。

## 1. 先定行为，再实现一个可用功能

项目采用规格驱动开发（SDD）：先把用户要完成的事、权限、错误情况和完成标准写清楚，再决定代码、数据库和接口怎样配合。Spec Kit 用于组织 `spec.md`、`plan.md`、`tasks.md`，分别回答“做什么”“怎么做”“按什么顺序做”。生成文件后仍需审阅，尤其要核对它是否符合已经确定的产品范围和[项目原则](../.specify/memory/constitution.md)。

实现按垂直功能切片推进。以“创建评测”为例，一个切片同时包含配置表单、目录兼容检查、质量确认、服务端身份与参数校验、数据库写入、成功／失败反馈，以及必要测试。这样每轮结束后用户能完成一件事，界面和后端的完成状态也能一起核对。

SDD 关注需求、设计、实现与验收的一致性；测试驱动开发（TDD）强调先写失败测试再写实现。本项目根据变更风险安排测试，并未把所有功能都按严格 TDD 实施。产品负责人确定范围并验收体验，Codex 协助开发和检查；工作台里的评测助手则是面向用户的业务功能。

## 2. 阶段 0–8 的实现顺序

### 阶段 0：产品定义

先确定平台要支持的场景：模型整体表现有变化时，怎样对比指标、找到异常样本，再填写并确认结论。围绕这条流程，确定两种演示身份的权限、MVP 范围和验收条件，形成 PRD。

需求依据岗位和领域分析，没有真实用户调研数据。固定合成故事用“总体成功率从 76% 到 81%，遮挡场景碰撞率从 8% 到 13%”说明总体改善可能伴随局部回退。它是演示数据，不代表实际业务收益。真实仿真器、模型训练、实时数据扫描、独立回补任务和人工分类流程不在当前范围内。

### 阶段 1：架构、数据与接口

采用 Next.js、TypeScript、Auth.js、Prisma 和 PostgreSQL，应用部署在 Vercel，数据库由 Neon 托管。整个系统是模块化单体：一个应用中按职责拆分模块。路由组合页面，应用层串联完整用例，领域层判断业务规则，仓储层通过 Prisma 访问数据库。

设计项目、模型版本、数据集、评测基准（Benchmark）、评测任务、指标、异常样本、复核记录、报告和审计之间的关系；同时确定会话、角色、状态流转、事务和 HTTP 错误结构。评测执行通过统一的 Provider 调用接口接入确定性模拟实现，方便以后替换执行来源。当前需求用同一个应用即可完成，没有引入微服务、消息队列或 WebSocket。

### 阶段 2：Figma 体验设计

先在 Figma 中梳理角色入口、任务选择、页面职责和主线流转，再补加载、空数据、失败、取消、无权限、窄屏和键盘操作。创建评测与版本比较各有入口；从板块进入先选任务，在结果、比较和异常页之间往返时持续携带当前任务及必要筛选条件。

原型用于提前发现交互问题，例如基线可不选时怎样展示结果、任务未完成时哪些操作可用、草稿与最终结论怎样区分。实现后再用实际页面核对原型。Figma 提供体验和视觉依据，数据写入与权限仍由应用实现和验收。

### 阶段 3：工程基础与身份入口

建立 Next.js 工程、Prisma Schema（数据库结构定义）、迁移、固定预置数据（Seed）和基础页面，接入 Auth.js 会话。访客输入共享访问密码后选择工程师或评测人员身份；服务端保护页面和业务接口，并处理登录、退出、会话过期和连续输错限制。共享身份适合受控演示，没有注册和个人账号体系。

这一阶段先打通“进入应用 → 读取数据库 → 按角色访问”的基础链路。检查登录后刷新、直接访问受保护地址、退出后的访问限制及窄屏体验，为后续业务切片提供可复用的身份和错误处理。

### 阶段 4：数据质量、模拟评测与任务管理

完成“自主配置 → 质量确认 → 创建任务 → 查看状态与结果”。服务端重新检查模型、数据集和 Benchmark 是否兼容：质量通过可创建，警告须明确接受，失败则阻断。基线可以不选；成功率目标用于判断是否达标，不参与生成模拟指标。

创建时保存配置快照，模拟 Provider 根据配置、随机种子（Seed）和评测回合（Episode）数生成可重复的结果。这里的随机种子是任务参数，用于固定结果，与初始化数据库的 Seed 脚本是两种用途。读取请求只读取数据，显式同步操作按服务端时间推进排队、运行和终态。页面展示任务状态，不把模拟执行写成真实后台仿真。

随后补齐多任务选择和管理：工程师最多同时保有三个进行中任务，可取消本人任务、为失败任务创建新 ID 重试、软删除本人终态任务。重复提交、并发容量、权限和状态变化均在服务端检查，重要操作写入审计。

### 阶段 5：模型对比与异常复核

先检查两个任务的项目、数据集、Benchmark、评测回合数和随机种子是否一致，再比较模型版本。整体和分场景差值保留单位、方向及样本数；无基线或口径不一致时说明原因。用户可从指标进入相关异常，再查看样本日志和人工结论。

工程师可保存本人任务的复核草稿，评测人员可确认最终结论。保存请求携带页面读取时的版本号；其他人已经修改时返回冲突，让用户重新读取并核对。当前结论、修改历史和审计在同一事务内保存，按变更情况标记报告过时；读取报告时还会核对完整来源。结果、比较、异常和报告入口保持任务上下文，形成连续的操作路径。

### 阶段 6：部署与运行维护

将 GitHub 中的应用连接到 Vercel，使用 Neon PostgreSQL 保存业务数据。运行时用连接池地址，迁移和维护用直连地址；开发、测试、预览和生产分别配置数据库。首次上线应用迁移并写入 Seed，日常发布只部署代码，新增数据库变化再执行增量迁移。

这一阶段同时建立 CI 检查、环境变量管理、自有域名与 HTTPS、上线验收及演示恢复入口。CI 检查代码，Vercel 构建并提供网页，生产验收检查实际操作和持久化。具体操作见下文[运行与部署](#4-运行与部署)。

### 阶段 7：公开交互主页

主页用对话式布局介绍产品、设计与实现过程，并链接 PRD、架构接口、Figma、开发流程和源码。体验入口进入既有访问密码页。文案和链接集中维护，人物动画引擎与页面排版分开，方便调整介绍内容。

人物由高清 WebP 序列帧组成。桌面鼠标和手机人物区拖动控制动作进度，换方向先回到共同待机姿态，再进入新动作；键盘也可操作。素材加载显示真实进度，失败可重试或选择静态浏览，减少动态效果设置会降低动画。验收同时检查人物外滚动、链接、加载失败、键盘和窄屏，主页介绍与业务入口始终可用。

### 阶段 8：评测调查 Agent 与单份系统报告

工作台加入常驻的 Q 版助手入口。assistant-ui 管理聊天界面，LangChain `createAgent` 将 OpenAI 模型与四个只读业务工具连接起来：读取评测概况、比较指标、筛选异常、读取样本证据。模型按问题选择查询，业务工具复用已有应用服务；服务端核对权限、任务归属和证据引用，并限制调用次数、时间、并发和累计费用。

每次登录生成新的访问标识，聊天同时归属于账号和本次登录。当前登录可切页、追问和刷新历史，同角色的另一位访客不能读取这段私聊。对话绑定明确的任务和基线，页面对象变化时由用户选择是否新建对话。成功回答附证据卡和“继续询问”，建议只预填输入框，用户发送后才开始下一轮模型调用。

报告页维护每个成功任务的一份当前系统报告。程序用固定模板整理当前指标、人工复核结论和限制，不调用模型，也不读取私聊。来源未变时重复生成复用原报告；来源变化时更新同一个 ID，记录更新前内容并清除旧确认。评测人员确认时，服务端同时检查角色、当前来源和页面读到的来源摘要，防止确认过时内容或他人更新后的未读内容。

结果页集中展示任务配置、状态、指标与待复核信息，旧总览地址保留兼容跳转。该阶段按约定由负责人手工验收真实问答、证据、历史、登录隔离、停止／失败、报告更新和确认冲突，不新增或运行 Agent 自动化测试。项目保持单 Agent 和现有单体部署，未引入文档 RAG、向量库、长期记忆或独立 Agent 平台。

## 3. 每轮功能怎样交付

开始一个功能前，先检查 PRD、当前规格和已确定的边界。涉及用户行为或范围变化时，先修正 `spec.md`；`plan.md` 再明确模块、数据迁移、接口、权限和事务；`tasks.md` 按依赖组织实施步骤。多个相关步骤可以在同一轮推进。

实现后按实际风险验证：

- lint 和类型检查发现代码与类型问题；相关单元测试核对业务规则，独立 PostgreSQL 集成测试核对真实写入、事务和并发行为，生产构建检查部署产物。
- 浏览器走查确认用户能完成主线，同时检查权限、刷新持久化、加载／空数据／错误、窄屏和键盘。页面能打开只是其中一项。
- 模型功能按阶段 8 的约定手工验收，检查实际工具调用、引用与保存；一轮问答可能包含多次模型请求。
- 行为变化同步功能规格；HTTP 变化同步 OpenAPI、错误结构和[接口示例](api-contract.md)。README 负责导航，避免在多个文件重复维护同一规则。

技术检查、浏览器验收和线上验证各有目的。完成前一阶段的交付和验收，再进入下一阶段；检查记录描述实际结果，不用设计稿、构建成功或历史记录代替当前功能验收。

## 4. 运行与部署

以下命令在包含 `package.json` 的 SimEval 仓库根目录执行，PowerShell 示例适用于本项目的维护脚本。使用 Node.js 22；依赖版本由锁文件固定。

### 平台与环境的职责

| 平台 | 在本项目中负责什么 |
|---|---|
| GitHub | 保存源码、规格和文档；GitHub Actions 在 main 分支 push 和 PR 时执行检查。 |
| Vercel | 安装依赖、构建和运行 Next.js；管理部署及应用环境变量。 |
| Neon | 提供 PostgreSQL，持久化任务、复核、聊天、报告与审计。 |
| Cloudflare | 管理自有域名的 DNS，按 Vercel 给出的记录连接域名与网站。 |

本地开发使用独立开发库或 Neon 开发分支，配置保存在被 Git 忽略的 `.env.local`。数据库集成测试使用 `.env.test.local` 中的 `TEST_DATABASE_URL`，库名必须是 `simeval_test`；CI 使用临时测试 PostgreSQL。Vercel Preview 连接预览数据库，Production 连接生产数据库。维护生产时使用独立的 `.env.production.local`，避免本地操作串到线上。

连接池让多个应用请求共用有限的数据库连接，适合网页运行；直连供迁移和维护使用。同一环境的两条地址必须来自同一个 Neon 分支、数据库和账号。

| 环境变量 | 用途与配置位置 |
|---|---|
| `DATABASE_URL` | 应用的 PostgreSQL 连接池地址；开发文件与 Vercel 各环境分别配置。 |
| `DIRECT_URL` | 迁移和维护使用的直连地址；维护文件必须与对应的运行地址指向同一库。 |
| `DATABASE_URL_UNPOOLED` | Neon 集成提供的直连变量，可作为 CLI 的兼容来源；生产维护文件统一使用 `DIRECT_URL`，便于核对。 |
| `AUTH_SECRET` | Auth.js 签名密钥，使用独立随机值。 |
| `ACCESS_PASSWORD` | 共享访问密码；首次 Seed 与该环境的应用部署使用同一配置。 |
| `OPENAI_API_KEY` | 服务端模型密钥，用于真实聊天调查。 |
| `OPENAI_MODEL` | 模型选择，须与 `src/server/agent/config.ts` 的模型和费用限制匹配。 |
| `ASSISTANT_BUDGET_USD` | 助手累计费用上限，由数据库账本记录用量和预留。 |

本机确需模型代理时可配置 `OPENAI_PROXY_URL`，它只影响模型请求；Vercel 不使用本机代理。真实连接、密码和密钥只保存在环境文件或平台变量中。

### 本地第一次启动

1. 运行 `npm ci`，按锁文件安装依赖，并由安装脚本生成 Prisma Client。
2. 将 `.env.example` 复制为 `.env.local`，填入开发环境变量。先核对数据库目标，再执行迁移。
3. 应用迁移并首次初始化固定合成故事：

   ```powershell
   npm run db:deploy -- --config=prisma7.config.ts
   npm run db:seed -- --config=prisma7.config.ts
   npm run dev
   ```

4. 服务启动后访问 `localhost:3000`，从主页进入登录，分别检查两种身份。聊天调查还需要模型配置；直接生成系统报告不调用模型。

`prisma7.config.ts` 是本仓库的 Prisma CLI 配置，命令显式指定它。迁移把仓库中的数据库变化按版本应用到目标库；Seed 写入固定故事。日常开发只需 `npm run dev`，新增迁移时再运行迁移命令；Schema 改动后运行 `npm run db:generate` 并重启服务。使用本机 PostgreSQL 时，可参考[本机初始化说明](../specs/004-deployment/quickstart.md#1-第一次启动)；Neon 无需运行管理员建库脚本。

### 首次生产上线

先在 Neon 准备生产分支，将它的运行地址配置到 Vercel Production。将 GitHub 仓库导入 Vercel，选 Node.js 22，安装命令为 `npm ci`，构建命令为 `npm run build`。Preview 与 Production 分别配置环境变量和数据库。模型相关变量在启用聊天调查时配置。

生产数据库初始化在维护终端中单独执行。先保存被 Git 忽略的 `.env.production.local`，其中的 `DATABASE_URL`、`DIRECT_URL` 必须指向同一生产库，`ACCESS_PASSWORD` 与 Vercel Production 一致。以下第一条命令只清除当前终端可能残留的同名变量，不修改配置文件：

```powershell
Remove-Item Env:DATABASE_URL,Env:DIRECT_URL,Env:DATABASE_URL_UNPOOLED,Env:AUTH_SECRET,Env:ACCESS_PASSWORD -ErrorAction SilentlyContinue
node --env-file=.env.production.local node_modules/prisma/build/index.js migrate deploy --config=prisma7.config.ts
node --env-file=.env.production.local --import tsx prisma/seed.ts
```

先确认迁移成功，再执行首次 Seed，然后部署应用或 Redeploy。构建只生成代码产物，不自动迁移、Seed 或恢复数据库。

在 Vercel 添加自有域名，按控制台给出的目标在 Cloudflare 配置 DNS，等待域名和 HTTPS 状态正常。DNS 负责把域名指向网站，HTTPS 负责加密浏览器与网站之间的通信；最终通过实际打开页面和执行操作核对访问。

### 后续发布与上线验收

普通发布先完成变更相关的检查，再推送代码，由 Vercel 构建新部署。若包含数据库变化，先备份并核对目标，只执行上面的迁移命令；现有库不再执行首次 Seed。环境变量修改后需要 Redeploy，新部署才会使用新值。数据库迁移与应用发布分别检查结果。

发布后从真实域名检查：

- 未登录不能进入工作台或调用业务接口；两种身份的登录、退出和角色权限有效。
- 创建评测、查看结果、取消／重试／删除、比较、草稿与确认可用，刷新后仍能读到保存内容。
- 助手真实问答有实际查询、文字流和有效证据，历史可恢复，同角色不同登录的私聊互相隔离。
- 系统报告可直接生成；重复生成复用同一份，来源变化后更新原 ID，确认检查过时与并发冲突。
- 窄屏、键盘、错误反馈和域名 HTTPS 正常；异常时能通过服务端日志和请求 ID 定位。

模型消息流的 HTTP 200 只说明请求开始响应，还要检查轮次终态、正文、证据和保存。网络可达性与首次素材加载速度依赖实际设备和网络，需要实测后记录，文档不据此承诺统一性能。

### 日常维护

代码发布与数据库变更分别管理。代码问题可回退 Vercel 部署；数据库变化通过迁移记录和备份处理。首次 Seed 用于初始化演示数据，增量补目录用于保留已有内容。

项目另有维护脚本，可将专用演示库恢复到默认数据。清理与重建在同一事务中完成，失败回滚，表结构与 AI 累计费用账本保留。网站没有恢复按钮，正常登录、构建和发布不会触发恢复；具体操作由维护者单独管理。
