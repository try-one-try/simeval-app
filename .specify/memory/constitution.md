# SimEval 项目原则

## 核心原则

### I. 黄金路径完整

每个阶段都服务于“配置评测 → 确认质量 → 创建执行 → 按需对比 → 异常复核 → 报告确认”的闭环。按可验收的垂直功能切片交付；涉及界面、服务端、持久化和校验的行为必须一起设计。加载、空数据、错误、无权限和成功状态均属于功能。

### II. 模拟与证据如实呈现

当前项目不运行真实仿真器、真实数据 ETL 或模型训练。合成数据、模拟执行、缓存结果和未经人工确认的 AI 报告必须显著标注。不得编造用户调研、线上使用量、性能提升或业务收益；假设、目标与已验证事实分别表述。报告只能引用当前任务中存在的指标和样本证据。

### III. 模块化单体与服务端边界

使用 Next.js 模块化单体。路由文件负责页面组合，业务规则进入应用层或领域层；Prisma 经仓储层访问 PostgreSQL。客户端组件不得访问 Prisma、密钥或仅服务端可用的模块。评测执行和 AI 分析通过 Provider 接口隔离，保留确定性模拟或缓存实现。未经明确决策，不引入微服务、消息队列、WebSocket 或额外基础设施。

### IV. 受控写入与可追溯状态

所有写操作在服务端完成身份验证、权限检查、参数校验和业务状态校验。重要状态变化写入审计记录；并发、幂等与事务边界按对应功能规格和 HTTP 契约落实。失败不能伪装为空结果或成功响应。

### V. 验收与文档同步

每个完成功能通过 lint、类型检查、相关测试和浏览器验收。使用确定性 Seed 数据，使演示故事可重复。行为变化更新对应功能规格；HTTP 变化同步更新 OpenAPI、错误结构、示例和相关测试。不得通过无说明的 `any` 或 `ts-ignore` 绕过 TypeScript。

## 工作流与权威出处

功能开始前先审阅 `specs/<功能>/spec.md`，解决关键歧义，再形成 `plan.md` 和 `tasks.md`；计划须符合本原则与[架构设计](../../docs/architecture.md)。实现后按规格核验并记录实际结果。项目 README 只说明目标和真实状态；HTTP 方法、参数、响应与错误以 [OpenAPI](../../docs/openapi.yaml) 为准。`.specify/` 模板和 `.agents/skills/` 是共享工作流文件，不是已完成业务功能的证明。

## 当前产品范围与变更

2026-09-27 原型认可：产品仅 ENGINEER／REVIEWER，无注册；基线可选、多任务明确上下文、本人任务取消／重试／软删除、自由文本结论与草稿／确认、报告来源版本。独立回补与人工分类退出 MVP，以简化真实任务主线。

本次修订影响 [002 规格](../../specs/002-quality-evaluation/spec.md)、架构及 planned 接口；旧 ADMIN／分类／回补数据需兼容迁移，八项请求字段仍沿用第一版；阶段 3 已落实双身份会话门禁，历史 ADMIN 不能进入产品。自主配置与删除等行为按规格分批实现。

## 治理

本原则记录已经决定的长期约束。变更原则时须说明理由、受影响的功能规格和迁移影响，并同步修订相关公开文档。功能范围、接口契约与实现发生冲突时，先明确决策并更新权威文件，再继续实施；任何阶段不得因工具生成了文件而跳过验收。

部署决策（2026-09-27）：Vercel＋Neon PostgreSQL，Prisma 与分层不变；旧 MySQL 迁移归档，新库 Seed 初始化。规格见[部署切片](../../specs/004-deployment/spec.md)。
